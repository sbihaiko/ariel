# Exit codes of the agent port

The registry of every `exit <n>` value the agent port answers. A number is assigned here before code uses it, and a number is never reused for another meaning. A reply always ends with one `exit` line; the word on the line before it names the reason.

`payload run --wait` reports the payload's own status on a `status <n>` line, then `exit 0`. A payload's status never appears on the `exit` line.

`payload run <name>` without `--wait` answers `pid <n>` then `exit 0` at once and runs the payload in the background, cut at its timeout. `payload logs <name>` shows what the payload printed, then `exit 0`; for a payload still running it waits until the payload exits. `payload list` marks a background payload that is still going as running.

A command line is tokens separated by spaces or tabs. Double quotes and single quotes group a token and are removed; inside double quotes `\"` and `\\` escape, and inside single quotes nothing escapes. Nothing is globbed or expanded: a `*` is a literal byte. A line holds at most 64 tokens and 4096 bytes; more tokens, or a line over the limit, answers `too_many_arguments` (exit 1), and an unbalanced quote answers `bad_quoting` (exit 1). Both are decided before any command runs. A connection ends after 60 seconds; a command still running then is stopped and answers `timed_out` (exit 1). `sleep` keeps its own ceiling of 0 to 60 seconds.

A target, a destination and every option value carry printable ASCII only, `0x20` to `0x7E`. Each byte outside letters, digits, `.`, `_` and `-` is written `%XX` in uppercase hex, and `%` itself is written `%25`, so the canonical action is injective and the owner's signer decodes it before showing it. A byte outside printable ASCII answers `bad_path` (exit 1), and so does a path with a segment that is `.`, `..` or empty; escaping makes bytes expressible, never traversal.

`head [N] PATH` and `tail [N] PATH` show the first or last N lines of a regular file, 10 when N is not given, and `wc PATH` answers `<lines> <words> <bytes> <path>`, where the lines are the newlines. A path that is not a regular file answers `not_a_file` (exit 1), and a count that is not a whole number answers `bad_argument` (exit 1). `ls`, `cat`, `grep` and `find` take `--limit N` before their operands. N is a whole number, and a limit that is not one, or any other option, answers `bad_option` (exit 1). Every reader answers at most 64 KiB, the cut marker included, and never refuses for being large. It shows its input in order, up to the limit and the cap; when it shows less than all of its input, it ends with `truncated <shown> of <total>` and exits 0. The units are lines for `ls`, `grep`, `find`, `head` and `tail`, and bytes for `cat`. A cut reader still reads its whole input to count it. The content of an answer stops at 64 KiB less the 64 bytes the marker may need. `truncated` is a marker, not an error word.

`date` takes no operand and answers one line, `YYYY-MM-DD HH:MM:SS UTC`, from the system's wall clock; a clock it cannot read answers `operation_failed` (exit 1). `du PATH` takes one path, absolute or relative to the session's directory, and answers one line per directory, `<bytes> <path>`, each directory's line after the lines below it and the names within a directory in byte order, so the operand's own total is the last line; the bytes are the total size of the regular files under that directory, a symbolic link is not followed and counts as no bytes, and any other file that is not regular counts as no bytes. A path that is not a directory answers its one line and nothing else. A relative path with no session answers `relative_path` (exit 1), a second operand answers `bad_argument` (exit 1), and any option answers `bad_option` (exit 1). `du` obeys the cap and the cut marker of the readers above, counting lines; a directory it cannot open still gets its line with the bytes it could count and answers that word, and a path it cannot stat answers that word and no line, and either way the answer exits 1. `dmesg` takes no operand and answers the kernel log, cut the same way; a platform with no kernel log a process may read answers `not available on this platform` (exit 1), as the host build does. `sysinfo` takes no operand and answers three lines, `uname <sysname> <release> <machine>`, `uptime <seconds>` and `memory <total_bytes> <free_bytes>`, or with `--json` the one object `docs/json-output.md` defines; a kernel that exposes no uptime or no memory figure answers `not available on this platform` (exit 1) and nothing else, and a uname it cannot read answers `operation_failed` (exit 1). On `date` and `dmesg` an operand answers `bad_argument` (exit 1) and any option, `--json` included, answers `bad_option` (exit 1); on `sysinfo` an operand answers `bad_argument` (exit 1) and an option other than `--json` answers `bad_option` (exit 1). `ifconfig` takes no operand and answers one line per interface address, `<name> <state> <address> <mask>`, sorted by name in byte order, where the state is `up` or `down` (administrative) and an interface with no IPv4 address answers `-` for the address and the mask; with `--json` it answers the objects `docs/json-output.md` defines. An operand answers `bad_argument` (exit 1), and any option other than `--json` answers `bad_option` (exit 1). A platform that cannot enumerate its interfaces answers `not available on this platform` (exit 1). `ping [-c N] [-W MS] ADDRESS` takes one literal IPv4 address and answers one line, `ping <address> <sent> <received> <min> <avg> <max>`, with the round-trip times in whole milliseconds rounded down, and exit 0 when at least one echo reply came back. `-c` takes 1 to 10 probes, 4 when not given, and `-W` takes 1 to 5000 ms per probe, 1000 when not given; there is no interval between probes, so the worst case is 50 seconds. A count or wait out of range answers `bad_argument` (exit 1), and so does a host name or an IPv6 address; an unknown option, `--json` included, answers `bad_option` (exit 1), a repeated `-c` or `-W` too, and no operand answers `missing_operand` (exit 1). When nothing is received, whether from silence or from an unreachable error, it answers `no_reply` (exit 1). The probe is a fixed echo request, and the reply bytes are never returned. A platform that cannot open an ICMP socket answers `not available on this platform` (exit 1) and nothing else. The optional diagnostics that are not built: `diff` and `netstat` are not on the agent port, and an invocation of one is gated and then answers `unknown_command` like any other unlisted command.

A shell command (`pwd`, `cd`, a read-only command that takes a path: `ls`, `stat`, `file`, `cat`, `head`, `tail`, `wc`, `grep`, `find`, `cmp`, `hexdump`, `df`, `du`, `sha256sum`, or an inspection command: `echo`, `help`, `id`, `sync`, `sleep`, `sum`, `sfoinfo`, `ps`, `procstat`, `sysctl`, `authid`, `date`, `dmesg`, `sysinfo`, `ifconfig`, `ping`) writes its output and its error word to the connection and ends with `exit <n>`, where `n` is the command's own status: 0 for success, 1 for an error such as `relative_path`, `no_working_directory`, `no_such_file` or `operation_failed`. `grep` and `cmp` also exit 1 when nothing matches or the files differ. A connection that names no session has no working directory: every path is absolute, and `cd` answers `no_working_directory` (exit 1) whatever it is asked. Inside a session, `pwd` answers that session's directory and `cd PATH` takes it there, judging the path exactly as `ls` judges one — `no_such_file`, `not_a_directory`, `symbolic_link`, `protected` and the rest answer for themselves and leave the session where it was — and an operand count other than one answers `bad_argument` (exit 1). `pwd` with no session still answers `/`.

`grep` takes `-r`, `-l` and `-c` in any order before its pattern, `-e PATTERN` to name a pattern outright, and `--` to end its options so that the pattern may begin with a dash. Any other leading word that begins with a dash answers `bad_option` (1) and is asked of no one.

`ls` takes `-l` and `-a` in any order before its path, and together. `-a` adds the entries whose name begins with a dot, which `ls` otherwise leaves out. `-l` answers one line per entry, `<mode> <size> <name>`: the mode as `ls -l` prints it (`d` or `-`, then nine permission bits), the size in bytes, then the name. Nothing follows the name, so a name with a space is the rest of the line. With `--json` and no `-l`, each entry is one object of `docs/json-output.md`; `--json` together with `-l` answers `bad_option`, because the JSON row already carries the three fields.

`find PATH` walks the tree under the path it is given, absolute or relative to the session's directory, and answers every name it finds, the root first. `-name PATTERN` keeps the entries whose name matches the pattern — matched against the name alone, not the path, with `*`, `?` and `[...]` expanded as bash's `find -name` does, and a value with no metacharacter matching exactly — and `-type f`, `-type d` or `-type l` keeps files, directories or links; the predicates may be given together, and `find` repeats them in no particular order. A predicate with no value answers `missing_operand`, and a type word outside `f`, `d` and `l` answers `bad_argument`, both with exit 1 and before anything is walked. Links are answered, never followed, and a link to a protected object answers `protected` (87).

The inspection commands add these error words, all with exit 1: `missing_operand` (an operand is required), `bad_duration` (`sleep` takes whole seconds from 0 to 60), `not_a_pid` (`procstat` takes a decimal pid), `no_such_process` (no process has that pid), and `not_sfo` (the file is not a PARAM.SFO). On the host build, `authid` answers `not available on this platform`, because it reads the console's kernel credentials. A `sysctl` write (`sysctl name=value`) or an `authid` with an operand is outside the read-only set, so it is gated like any other unlisted command.

`read <path> [--offset <n>] [--limit <n>]` is a read-only command that answers in binary, without asking. Its answer is a header `bytes <size> <sha256>`, then exactly `<size>` raw bytes, then `exit 0`, which is the one frame of ADR-0012 decision 5. `<size>` is the number of bytes that follow: the file's size for a whole read, the range's length for a cut one. `<sha256>` is the whole file's SHA-256, so an agent that assembles ranges can verify the result, and an agent that needs the file's size asks `stat`. The range starts at `--offset` (0 when absent) and holds at most `--limit` bytes (the rest of the file when absent). No answer carries more than 64 KiB: a range longer than that is cut to 64 KiB and followed by `truncated <shown> of <total>`, then `exit 0`, where `<total>` is the length of the range asked for (the file's size less `--offset`, or `--limit` when that is less). An offset past the end answers `bad_range` (exit 1); an offset equal to the size reads nothing. An option other than `--offset` or `--limit`, one given twice, a value that is not decimal, or a missing value answers `bad_option` (exit 1). A directory answers `is_a_directory` and any other file that is not regular `not_a_file`, both exit 1. A protected path answers `protected` (87), through a link too, as every file command does.

The file commands `mkdir`, `rmdir`, `touch` and `rm` take one path, absolute or relative to the session's directory. Each one answers `approval_required` (75) with a challenge first, and runs only after the owner signs it. The challenge binds the path and the entry's identity (kind, device and inode); the approval is single-use. Any other command outside the read-only set is gated the same way and then does nothing, answering `unknown_command`. A write outside `/data`, `/user` and `/mnt/usb*` answers `protected` (87) without asking. `rm -r PATH` and `cp -r SOURCE DEST` take the whole tree below their operand and ask once for it; a symbolic link anywhere in the tree answers `symbolic_link` (1) before anything is asked or removed, and a link to a protected object answers `protected` (87). A tree 64 levels deep or deeper answers `operation_failed` (1) without asking, and neither copies nor removes anything. Any option a file command does not take answers `bad_option` (1) and asks nobody.

An executable is run by its absolute path, or by a bare name the `PATH` holds. Its first answer is `approval_required` (75) with a challenge. The challenge binds the resolved path, the file's SHA-256, its identity (kind, device and inode) and its arguments, one option each; the approval is single-use. After a grant the same command runs the bytes that were hashed, prints the payload's output, and answers `status <n>` with its own status, then `exit 0`. A file changed or replaced after approval answers `approval_stale` (78) and does not run. A run with other arguments than were signed answers `approval_stale` too, and a granted approval it finds is spent by that answer. A run never follows a symbolic link: a path, or a `PATH` entry, that is one answers `symbolic_link` with exit 1 and no challenge. A file over 64 MiB answers `too_large` with exit 1 and no challenge. A run with more than eight arguments, or an argument over 64 bytes, answers `unknown_command` with exit 1 and no challenge. An argument carries the same printable ASCII as any option value and is escaped in the canonical action; a byte outside printable ASCII answers `bad_path` with exit 1 and no challenge. The audit log records `run.request`, `grant`, `run.start` before the payload starts, and `run.status` after it returns, whose fifth column is `status-<n>`; a payload the loader cannot start is `run.failed`.

`kill <pid> <SIGNAL>` is gated like a payload commit: it answers `approval_required` with exit 75 until the owner signs its challenge, which binds the pid, the signal and the process's start identity. After a grant, the same command runs once and answers `killed <pid> <SIGNAL>` with exit 0. Its error words are `bad_signal` (the signal is not TERM, KILL, INT or HUP), `no_such_process` and `kill_failed`, all exit 1; a pid that is not a decimal number answers `unknown_command`, and a kill with another argument count is an unlisted command, gated like any other. The audit log records `kill.request`, `kill.done`, `kill.stale`, `kill.failed` and `kill.protected`, like the file commands. Exit 87 (`protected`) covers a kill of a critical process and of Ariel's own process; those are refused whether or not an approval exists. A process that was restarted under the same pid answers `approval_stale` with exit 78, and its approval is spent.

`chmod MODE PATH`, `chown ID PATH` and `chgrp ID PATH` are gated the same way. The mode is octal up to `07777`; the owner and group are decimal ids below 4294967295. The challenge also binds the requested mode, owner or group, so a different one answers `approval_stale`. A bad operand answers `bad_mode`, `bad_owner` or `bad_group` with exit 1 before anything is asked; a missing one answers `missing_operand`. A symbolic link to a protected object answers `protected` (87), and the link is never followed to change its target.

The transfers `cp`, `mv` and `ln` take a source and a destination, each absolute or relative to the session's directory. The source must be a regular file (a directory answers `is_a_directory`, a symbolic link `symbolic_link`, a file that is not regular `not_a_file`), and the destination must not exist (`exists`, exit 1); nothing is ever replaced. Each one answers 75 with a challenge that binds both paths, sha256 `none`, and the source's identity, and runs only after the owner signs it. `cp` copies the bytes and leaves the source; `mv` renames the source to the destination, and copies and then removes the source only when the rename answers `EXDEV` (across filesystems). The destination name is reserved with an exclusive create before the rename, so an object that appears there after the check is kept and the answer is `exists`; the rename can only replace that empty reservation. A process that can write the destination directory could still replace the reservation between its last check and the rename, and Ariel does not close that window, since it uses no no-replace rename. `ln` makes a hard link, which this console refuses with `operation_failed` (exit 1) on both `/data` and the USB volume, measured on 11.20. A source that changed after the signature answers `approval_stale` (78), and nothing moves. Every path involved is checked for protection: the source and destination, the directories above them, and the target of a symbolic link, so a link to the token answers `protected` (87) even when approved. A pair of paths whose audit subject would be longer than 180 characters answers `bad_path` before anything is asked.

`ln -s TARGET PATH` makes a symbolic link at PATH whose text is TARGET, taken as written and not resolved against the session's directory. TARGET must be absolute, or the line answers `bad_path` (exit 1) before anything is asked. PATH must not exist (`exists`, exit 1). A TARGET that names a protected object, or a link to one, answers `protected` (87) before anything is asked; a TARGET reached through a link on the way is followed as the kernel follows it, so the check covers the object it really names. Otherwise the line answers 75 with a challenge that binds the command `ln.symlink`, the link's path and its target text, and the link is made only after the owner signs. A filesystem that cannot hold a symbolic link answers `link_unsupported` (exit 1) when `symlinkat` answers `EOPNOTSUPP`, and nothing is created; any other refusal answers `operation_failed` (exit 1). The errno the exFAT stick answers has not been measured, so `link_unsupported` on the stick is not yet confirmed. A link is never a transfer's source or a write's or unzip's destination: each answers `symbolic_link` (exit 1), or `exists` for a write, and no write goes through a link. `file` on a link answers `<path>: symbolic link` after the protection check on its target; the other reads still follow a link to an ordinary file, and a link to a protected object answers `protected` to all of them.

`write <path> <size> <sha256>` writes the bytes that follow the command line, as `payload push` does: exactly `<size>` bytes, then the client closes its sending side. A size over 64 MiB answers `too_large` (exit 1) before the body is read and before anything is asked. A path outside `/data`, `/user` and `/mnt/usb*`, the token, the approval state, the nonces, the state directory, a link to any of them, and an existing protected object answer `protected` (87) before the body is read, with or without an approval. A body whose size or hash does not match answers `upload_mismatch` (81), as `payload push` does. Otherwise `write` answers `approval_required` (75) with a challenge that binds the path, the size and the SHA-256; the body is sent again with each attempt, since nothing is kept on the console. A destination that already exists answers `exists` (exit 1) once the body is read, before anything is asked, and nothing is replaced. After the owner's grant the same command creates the file exclusively, writes the body and answers `exit 0`. A destination that appeared after the grant answers `approval_stale` (78), and nothing is written. The audit log records `write.request`, `write.done`, `write.stale`, `write.denied` and `write.refused`; a refusal for protection, existence, size or a failed write is `write.refused`. A body that does not match answers `upload_mismatch` without an audit line, as `payload push` does.

`tar -t ARCHIVE` lists a ustar archive at once: one member name per line, then `exit 0`. `tar -x ARCHIVE DEST` answers `approval_required` (75) with a challenge that binds the archive's sha256, its identity (kind, device and inode) and the destination; it extracts only after the owner signs, and an archive or destination that changed since then answers `approval_stale` (78). A member whose name is absolute or climbs out of the destination (`../`) answers `escaping_member` (1), and a link member that leaves the destination answers the same. A member that is not a plain name, a directory, a file or a link answers `bad_member` (1), and a link inside the destination is refused as `bad_member` too, since this slice does not extract links. A file that is not a ustar archive answers `not_a_tar` (1). Every member is checked before the first one is written, so a refused member leaves nothing behind. A member whose path already exists under the destination answers `exists` (1). The archive or destination being a protected object answers `protected` (87) even with an approval.

The system commands `mount -t <fstype> <from> <dir>`, `umount <dir>`, `chroot <dir>` and `mknod <path> b|c <major> <minor>` are gated like the file commands. Their challenge binds the target, the options (the file system type and source for `mount`; the type, major and minor for `mknod`) and the target's identity. A wrong argument count or shape answers `bad_argument` (1) without asking. A target, or a symbolic link to one, that is a protected object answers `protected` (87) even with an approval. On the host build, which cannot run them, a signed command answers `not available on this platform` and `exit 1`; the attempt is audited as `<command>.unavailable`.

`env NAME`, `export NAME=VALUE` and `exec <path> [args]` are gated the same way. Each one answers `approval_required` (75) until the owner signs its challenge, and each signed action names one thing: `env` the variable, `export` the variable and the hash of its value (inside a session, `export` also carries `option.scope=session`), and `exec` the program, the hash of its bytes, and its arguments (their count and a hash). A grant runs the command once. `env` prints `NAME=value` when the variable is set, then `exit 0`; `export` answers `exported NAME` with exit 0; `exec` runs the program, prints its output, then `status <n>` and `exit 0`, where `<n>` is the program's own status. A changed value, argument list or program answers `approval_stale` with exit 78 and runs nothing. The words `bad_name` (exit 1) refuse a name that is not a letter or `_` followed by letters, digits or `_`, of at most 32 characters, and `export_failed` and `value_too_long` (exit 1) refuse a variable that cannot be set or shown. `exec` names the program by its absolute path, so a relative one answers `relative_path`; it answers `bad_path`, `no_such_file`, `not_a_file` and `symbolic_link` as the file commands do, and `too_large` (exit 1) for a program over 64 MiB. A program outside the root answers `protected` (87) without asking, as does a protected object such as the token. The audit log records `env.request`, `env.done`, `env.failed`, `env.denied` and `env.refused`; the same set for `export` and `exec`, with `export.stale`, `exec.stale`, `exec.failed` and `exec.protected` as well; and each refusal of a name or a path.

`unzip -l ARCHIVE` lists the archive's members as `size name` lines, then `exit 0`, at once and without asking. `unzip ARCHIVE DEST` answers 75 with a challenge that binds the archive's sha256 and the destination, and extracts only after the owner signs it. The archive is read whole, up to 16 MiB, and only its stored members are accepted: an archive that is not a zip, is larger than 16 MiB, has a deflated, encrypted, zip64 or multi-disk member, a duplicate name, or a control character in a name answers `bad_archive` (exit 1). The destination must be an existing directory; an existing member answers `exists`. A member whose name is absolute, holds `..`, a backslash or an empty part refuses the whole archive with `unsafe_member` (exit 1) before anything is asked or written. An archive changed after the signature answers `approval_stale` (78). The archive and destination are both checked for protection, through links too, and answer `protected` (87) even when approved. The audit log records `unzip.list` for a listing, and `unzip.request`, `unzip.done` and `unzip.refused` for an extraction. A segment that is `.`, `..` or empty is refused as `bad_path`; a dot inside a segment is an ordinary byte and is carried and escaped.

The built-ins `launch`, `pkg_install`, `hbldr`, `hbdbg`, `suspend`, `notify` and `reptyr` are gated the same way: each answers `approval_required` (75) with a challenge first, and runs once through its own process after the owner signs it. The challenge binds the command and its target (the title ID for `launch`; the operand as written for `pkg_install`, a path or a `file://` URI; the path for `hbldr` and `hbdbg`; the word for `notify`; `suspend` itself; the pid for `reptyr`), each argument after the target as text (options `arg1` to `arg5`, in order), and for a file the entry's kind, device and inode; `reptyr` binds the process start identity instead, like `kill`. A changed argument, entry or start answers `approval_stale` (78), and the approval is spent. A missing operand answers `missing_operand`; a `reptyr` pid that is not decimal, an argument over 64 bytes, or a sixth argument after the target answers `bad_argument` (exit 1) before anything is asked. A target or an argument carries printable ASCII and is escaped in the canonical action; a byte outside printable ASCII answers `bad_path` (exit 1) before anything is asked. A relative path, a path that is not a regular file, and a protected path are refused with their usual words before anything is asked. `pkg_install` also takes a package as the `file://` URI it documents, `file://` followed by an absolute path and no authority: the path part is checked as a path, the operand as written is signed, and the payload receives the local path it names. A `file://` URI with any other authority, or with a relative path part, answers `bad_path` (exit 1). On the host build a granted built-in answers `not available on this platform`, because it needs the console, except `pkg_install`, which answers the app-directory fact below. The audit log records `<command>.request`, `<command>.done`, `<command>.stale`, `<command>.denied`, `<command>.refused` and `<command>.protected`. `suspend` is also the standby route: it suspends the console rather than restarting it, which is all `reboot(2)` ever did on this firmware, and it is the command the table points at for a standby.

`pkg_install` answers a fact it measured after the call, not the call's return: the install is asynchronous and the API returns once the request is accepted. After the built-in exits 0, the agent waits for the app directory the title's own parameter file names, `/user/app/<title ID>` where the title ID is the one the package's own name carries before its first `-`, then checks the title's parts. A finished install's last line is `installed <TITLE> <bytes> <sha256>` with `exit 0`: the title, the byte count and the SHA-256 of the source package it installed. An install that did not finish answers `install_incomplete <TITLE> <part>` with `exit 1`, where part is the first missing one of `package` (the built-in's exit status is nonzero, the name carries no title ID, the app directory did not appear within the 45-second wait, an entry of the app directory, `app.pkg` among them, is absent or empty, or the source package is not a regular file or cannot be read for its hash after the install), `sfo` (the title's `sce_sys/param.sfo` is absent, empty or has no `CONTENT_ID`), `appmeta` (the `/user/appmeta/<TITLE>` entry is absent), `licence` (the licence for the title's content ID is absent or names another one) or `unknown` (a verify finding that no part is assigned to, so a finding added later is never read as a missing package). A package whose name carries no title ID answers `install_incomplete - package`, because no directory can be measured. A package over 256 MiB (268435456 bytes) is not read for its hash: a finished install over that ceiling still answers `installed <TITLE> <bytes> -` with `exit 0`, the dash standing where the SHA-256 would be, so a caller reads a finished install as finished. The byte count is the package's size in bytes. The source package is never deleted, and cleaning it is a separate, gated `rm`. The host build has no installer: a granted `pkg_install` is accepted and installs nothing, and the same answer is read from `user/app/<title ID>` and the title's parts below the test root, so a scenario says whether the title appeared by making it.

`sfocreate` is gated like the built-ins above: the last operand is the output path and every operand before it is bound as text, `arg1` first, so the owner reads the options too. The options are checked before the owner is asked: an unrecognized option answers `bad_option`, a key-value pair that is not `KEY=VALUE`, or an `-i` value that is not a decimal integer, answers `bad_argument`, and a `-s` string size, or an output, over 1 MiB answers `too_large` (all exit 1). A path outside `/data`, `/user` and `/mnt/usb*`, the token, the approval state, the nonces, the state directory, a link to any of them, and an existing protected object answer `protected` (87) without asking. An output that already exists answers `exists` (exit 1) before the owner is asked, and nothing is replaced. After the owner's grant the same command writes a PARAM.SFO, created exclusively, and answers `exit 0`; an output that appeared after the grant answers `approval_stale` (78) and nothing is written. The host build creates the file too, because the command needs no console. The audit log records `sfocreate.request`, `sfocreate.done`, `sfocreate.stale`, `sfocreate.denied`, `sfocreate.refused` and `sfocreate.protected`.

`shutdown` takes no argument and is gated: it answers `approval_required` (75) with a challenge that binds the command `shutdown`, the target `console`, the ordered list of mounted removable volumes it will unmount (`/mnt/usb0`, `/mnt/usb1`, both joined as `/mnt/usb0,/mnt/usb1`, or `none`) and the sha256 of that list. After a grant, the same command answers `shutting_down` with exit 0 and the console's own shutdown path takes the console down: `sceShellCoreUtilRequestShutdown` has the system unmount those volumes, run the `/user` cleaner and power off (#135, `system-spike.elf`). The answer and its audit line are written before the call, which ends the connection with it; the command never claims the console is off, and nothing claims it came back on. A shutdown the owner denied answers `approval_denied` (77), and a mount list that changed after the signature answers `approval_stale` (78); neither shuts anything down. A shutdown whose mount list cannot be read answers `shutdown_failed` (exit 1) and is audited as `shutdown.failed`. A request the console refuses comes after the answer is already sent, so it cannot change it: the connection still ends with `shutting_down` and `exit 0`, and the audit log records `shutdown.failed` after `shutdown.done`. The audit log records `shutdown.request`, `shutdown.done`, `shutdown.stale`, `shutdown.denied` and `shutdown.failed`.

`reboot` takes no argument. On the console build it answers `reboot_unsupported` with exit 1 before anyone is asked: no call from a payload restarts this console, as the probe behind #135 measured — `reboot(2)` puts it into standby, `sceSystemServiceRequestReboot`, `sceSystemStateMgrReboot` and `sceSystemServiceRequestPowerOff` answer success and change nothing, and `sceApplicationSystemReboot` is refused. It makes no challenge and calls nothing, and the audit log records `reboot.unsupported`. The host build keeps a working `reboot`, which restarts Ariel's own process and runs the boot list: it answers `approval_required` (75) with a challenge that binds the command, the target `console` and the sha256 of the autoload list the restart will run, and after a grant answers `rebooting` with exit 0. A host reboot the owner denied answers `approval_denied` (77), a changed autoload list answers `approval_stale` (78), and a restart that cannot start is audited as `reboot.failed`. For that host restart the audit log records `reboot.request`, `reboot.done`, `reboot.failed`, `reboot.stale` and `reboot.denied`, and the restart runs the autoload entries as a boot does; a restart without that, as after a crash, runs none of them.

`autoload safe-boot` takes no argument and is gated: it answers `approval_required` (75) with a challenge that binds the command `autoload.safe-boot`, the target `autoload` and the sha256 of the boot list it leaves aside. After a grant, the same command answers `autoload safe-boot` with exit 0. The boot list is set aside, leaving only Ariel in it; the next start of Ariel restores it, so the skip lasts exactly one boot. A safe-boot the owner denied answers `approval_denied` (77), and a changed boot list answers `approval_stale` (78); neither changes the list. A second safe-boot while one is pending answers `safe_boot_pending` (exit 1) before anything is asked. The audit log records `autoload.safe-boot.request`, `autoload.safe-boot.refused`, `autoload.safe-boot.stale`, `autoload.safe-boot.denied` and `autoload.safe-boot.failed`, the change as `autoload_safe_boot`, and the restore as `autoload_restore`.

`payload config <name> kind=one-shot timeout=<s>` is gated like the commands above and answers `configured <name> kind=one-shot timeout=<s>` with exit 0 after a grant. A payload with no declared kind is one-shot. `unsupported_kind` (exit 1) refuses any other kind, `bad_argument` (exit 1) a timeout that is not a whole number from 1 to 3600 seconds (`HEALTH_TIMEOUT_MAX_S`, so a check that hangs blocks its connection for at most an hour), and `config_failed` (exit 1) a record that cannot be written. The audit log records `payload.config.request`, `payload.config.done` and `payload.config.failed`.

An activation runs the payload's one-shot health check: a commit or a rollback starts the build with no arguments, and it is healthy only if it exits 0 within its timeout (30 s when none is configured). Its output goes to the payload's log, never to the reply. An ad-hoc `payload run` starts no health check. A failing check answers `health_failed <name> <sha256>` with exit 1 after the build is replaced by the previous version (audited as `health.replace`), or, with no previous version, is marked failed and removed from autoload (audited as `health.failed` and `autoload_remove`). `payload list` shows such a build with `failed=yes`. The check's own events are `health.start`, `health.ok`, `health.fail` (id `-` when the log cannot be opened, `spawn` when the build cannot be spawned) and `health.timeout`.

Four exit-1 words cover a check whose outcome is not a clean replacement or mark, and each says what changed. `health_not_run` answers an activation whose build could not be looked up after the commit or rollback: the new build is current and was never checked; it is audited as `health.skipped`. `health_unrecorded` answers a failed check whose store change did not happen at all: nothing is replaced, removed or marked, and it is audited as `health.skipped`. `health_partial` answers a failed check whose build was removed from autoload but could not be marked failed: the build is no longer in autoload, `payload list` does not show `failed=yes`, and it is audited as `health.partial`. `audit_failed` answers a change that took effect whose audit line could not be written; for a removal from autoload, the `autoload_remove` line is missing.

The payload list line is `payload <name> source=... version=... release=... asset=... sha256=... path=... running=yes|no failed=yes|no previous=<sha256|->`. `failed` is always present and sits before `previous`, which stays last.

A build that pins no anchor refuses every gated command, and `key adopt-anchor` cannot seed it because the anchor it would adopt is what the build lacks. That state answers `no_anchor` (exit 1) rather than `key_refused`, because it names the build and not the keyring: an empty or mismatched keyring is the owner's to fix from the port, and a missing anchor is not. The audit log records the refusal with the command that answered it, as it does for `key_refused`.

`key revoke --since <N> <primary>` is gated and must be signed by the current recovery key; it passes while frozen and while every approval slot is in use. `N` is a generation the keyring has reached, as a decimal number: a generation not yet reached, or a primary the keyring would refuse, answers `key_refused` (exit 1) before the owner is asked, and anything else answers `bad_argument` (exit 1). After a grant it answers `key_revoked <generation>` with exit 0. Every primary from generation `N` to the current one is declared compromised: each grant the grant ledger holds from those generations (an install, a pin, an autoload entry) is suspended, a suspended autoload entry leaves the autoload file, `<primary>` becomes the primary at the next generation and the old primary is retired. The freeze, if any, stays. Grants from before `N`, grants of a key retired by `key rotate` before `N`, and pins the allowlist set in advance stay active. The keyring, the ledger and the autoload file change in one journal transaction whose steps are `prepared`, `committed`, `suspended`, `autoload`, `renamed` and `audited`. The audit log records `key_revoke`, then `grant_suspended <name> <kind> <sha256|none>` for each grant suspended; a refused or stale revocation is audited as `key.revoke` `refused`, `stale` or `failed`. A revoked range is never lifted; a grant of it is restored only by approving it again with an active key.

`addon check <name>` and `addon list` read the addon directory `/data/ariel/addons` and never ask the owner. Each entry of that directory is an addon; an entry that is not a directory answers `manifest_missing`. An addon's `manifest` is a regular file of at most 512 bytes: `key value` lines, one space between key and value, each key exactly once and in any order. The keys are `name <name>`, which must equal the directory's name; `args <min>-<max>`, the number of arguments the addon takes, from 0 to 8, with `min` not above `max`; `abi <n>`, the Ariel ABI the addon was built against; and `platform <ps5|host>`. Any other line, key or value, or a missing or repeated key, is malformed. This build is ABI `1` and platform `host` on the host build, `ps5` on the console. `addon check <name>` answers `addon <name> ok` and `exit 0` for an accepted manifest. A manifest naming another ABI answers `addon_refused <name> abi`, one naming another platform answers `addon_refused <name> platform`, both with `exit 1`; when both differ the `abi` field is named. A missing manifest answers `manifest_missing <name>` (91) and a malformed one `manifest_malformed <name>` (92). A name that is not a valid payload name answers `bad_name` (exit 1). `addon list` prints one line per addon, in no particular order: `addon <name> ok`, or the refusal with its name (and field, for `addon_refused`), or a bare `bad_name` for an entry whose name is not a valid payload name; then `exit 0`. One bad manifest hides none of the others. A missing addon directory lists nothing and exits 0; one that cannot be opened answers `operation_failed` and `exit 1`, to `addon list` and `addon check` alike.

`addon run <name> [args...]` is gated and asks the owner, with the challenge naming the command `addon`, the addon's name, the manifest's SHA-256, the argument count as `option.argc` and each argument as `option.argN`, from `option.arg0` to `option.arg7`. An addon directory that holds a `server` file adds `option.server`: that file is one line of 1 to 64 printable ASCII bytes with no space, the server the owner set for the addon, which the owner signs and which the addon reads again itself. Before the owner is asked, the manifest is judged as `addon check` judges it, and the argument count must lie within the manifest's `args` range; a count outside it answers `addon_refused <name> args` with `exit 1`, and a `server` file that is empty, over 64 bytes or not one such line answers `addon_refused <name> server` with `exit 1`. More than eight arguments answer `too_many_arguments` (exit 1) before the manifest is read. Each argument carries printable ASCII up to 255 bytes, the longest path the FTP addon takes: a byte outside printable ASCII answers `bad_path` (exit 1), and a longer argument answers `bad_argument` (exit 1). The arguments together must fit the 2048-byte action the owner signs, or the run answers `too_large` (exit 1) before the owner is asked; two arguments of 255 bytes always fit. The addon's `elf` file is then run in a process of its own with the arguments and an empty environment, so the token, the keyring and the state directory are not passed. Its standard output and standard error together are its result. The run is cut at 10 seconds and answers `timed_out` (exit 1); output past 64 KiB answers `too_large` (exit 1); a non-zero exit or a death by signal answers `operation_failed` (exit 1); a spawn that fails answers `spawn_failed` (exit 1). An addon that exits 3 refused a path and answers `bad_path` (exit 1); one that exits 87 named protected state and answers `protected` (87). The output goes to a new file `/data/addon-<name>-<ms>` as the addon writes it, where `<ms>` is the platform clock in milliseconds. A run that ends badly after its addon started keeps that file: it answers its word, then `result /data/addon-<name>-<ms>`, then `exit 1` (`exit 87` when the word is `protected`), so the addon's own message reaches the agent through the file, which the agent reads with `cat`. A `spawn_failed` run has no output and names no file, and a run that fails before its addon starts answers its word alone. A run that ends with status 0 keeps that file and answers `result /data/addon-<name>-<ms>`, then `status 0` and `exit 0`. `result` is a reply line, not an error word. The audit log records `addon.request`, `addon.stale`, `addon.denied` and `addon.refused` as every gated command does, `addon.done` before the run and `addon.failed` for each failed outcome. A refusal before the owner is asked (`addon_refused`, `manifest_missing`, `manifest_malformed`, `bad_name`, `too_many_arguments`, `bad_path`, `bad_argument`, `too_large`, or an `elf` that cannot be opened) is audited as `addon.refused` with no `addon.request`.

`shots --last`, `shots --count <n>` and `shots --minutes <n>` copy images the console's Create button wrote, from `/user/av_contents/photo` into `/data/shots`. `n` is a decimal from 1 to 64. The command is gated: the challenge names the command `shots`, the target `/data/shots` and the selector as `option.select`, `count:<n>` or `minutes:<n>`, so a grant for one selection does not run another. Before the owner is asked, a missing selector or a selector the command does not take answers `bad_option` (exit 1), and an `n` outside 1 to 64 answers `bad_argument` (exit 1). A gallery that holds nothing the selector keeps, or that does not exist, answers `no_shots` (exit 1) and asks nobody. After the grant, each copied image is one line `shot <path> <bytes> <sha256>`, newest first, and then `exit 0`. The audit log records one `shots.done` line per image, carrying that path and that sha256; the size stays on the reply line. A copy that fails, a gallery that cannot be read, or more than 64 images, answers `shots_failed` (exit 1). The gallery is only read; the copies are the agent's to read and to remove with the gated `rm`.

A command line whose first token begins with `@` carries a session prefix: the token is `@` followed by the session ID, and the rest of the line is the command, run as it would run without one. A first token that begins with `@` and is not `@` plus exactly 32 lowercase hex characters, or that names a session which is not live, answers `session_expired` (93) before the rest of the line is read as a command and before any gate: it never reaches the unlisted-command path, so a typo asks nobody. Using a session this way restarts its idle clock. A path operand resolves against the session's directory before it is judged and before the gate: the join is lexical, `.` and `..` are normalized, a `..` that would leave `/` answers `bad_path` (exit 1), and the canonical action carries the resolved absolute path. The commands that resolve one this way are the shell commands, the gated file commands and transfers, `write`, `unzip` and `tar`; `exec`, `sfocreate` and the built-in file commands (`pkg_install`, `hbldr`, `hbdbg`) still take an absolute path and answer `relative_path` for a relative one; `pkg_install` also takes a `file://` URI of an absolute path. A line that is only the prefix answers `unknown_command` (exit 1) and asks nobody. The prefix carries no authority — a gated command inside a session still answers `approval_required` (75) and its challenge, and the session ID never enters the canonical action.

`session new`, `session close <sid>` and `session list` are the Stage 5 lifecycle, and none of them asks the owner: they move no bytes and change nothing outside Ariel's process, except that `session new` and `session close` each append one audit line. `session new` answers `session <sid> ttl <seconds>` and `exit 0`; the ID is 32 lowercase hex characters, and the TTL is the idle window in seconds. `session list` answers one line per live session, `session <sid> idle <seconds> cwd <path> env <n>`, then `exit 0`. `session close <sid>` answers `session_closed <sid>` and `exit 0`, and closing a session that is not live answers `session_expired` (93). Eight sessions may be live at once and the ninth answers `session_full` (exit 1). A session nobody used for its TTL leaves the table, and its ID answers `session_expired` from then on. The audit log records `session.new` and `session.close`, each with `-` in place of the target, so an ID never lands in the log; a refused close, a `session_full` and a lookup that finds nothing write no line. `session` with any other word or count of them answers `bad_option` (exit 1) and asks nobody. A session carries no authorization: every gated command inside one still asks the owner, and the session ID never replaces a signature.

A session carries an environment of its own. `@<sid> export NAME=VALUE` writes the session's map, and its challenge carries `option.scope=session` and never the session's ID, so a grant for one session's export does not run another's. `@<sid> env NAME` answers the session's value when the session holds the name, and the process's own value when it does not, so the answer is the session's layer over the process environment. The map belongs to the session and to nothing else: any connection that names the same session ID reaches it, no process variable changes, another session does not see it, and it leaves the table with the session, whose ID then answers `session_expired` (93). A payload run in the foreground, a payload run in the background and an `exec` started from a session all receive the session's layer over the process environment, copied at the moment of the spawn, so a later `export` in that session does not change a payload that is already running. An addon still runs in a process with an empty environment and never sees a session. A session holds at most 16 names, a name is at most 32 bytes and one assignment at most 1024 bytes: a seventeenth name answers `export_failed` (exit 1), a longer name answers `bad_name` (exit 1) before the owner is asked, and a longer assignment answers `value_too_long` (exit 1). Outside a session `export`, `env` and `exec` behave and sign exactly as they did: `export` sets the process variable, `env` reads it back from the process environment, and `exec` hands the program that same environment. A session layers its own names over that process environment, so a value exported outside one is visible inside it, and `@<sid> export` changes only the session's map.

The verify and trace verbs add these words, which have no row of their own. `verify TITLE` checks one installed title and answers one line per check: `ok <check>` or `finding <kind> <detail>`, then a status line. The status line is the word `whole` followed by the title when every check holds, with exit 0, and the word `not_whole` followed by the title when any does not, with exit 1. The word `not_installed` followed by the title is the whole reply for a title whose directory is absent, with exit 1. The word `too_large_to_verify` followed by the entry is the line of a hash check whose file is over 256 MiB (268435456 bytes): the file is not read, that check does not hold, and the status is `not_whole`. A title's layout under the console's root is `user/app/<TITLE>/` holding `app.pkg`, `app.pbm`, `app.json`, `app.xml` and `sce_sys/param.sfo`, which must each be a regular file of at least one byte; `user/appmeta/<TITLE>` is its metadata entry, which must exist; and its licence is a file `user/license/fake<CONTENTID>.rif` whose content ID contains `-<TITLE>_`. The content ID is compared with the `CONTENT_ID` entry of the title's `PARAM.SFO`, never with the title's directory name. A title with no licence answers `finding licence_missing`, and the content ID is compared only when one is found. `trace_unchanged` is the one word a diff with no changed field answers, with exit 0: it is a successful answer, distinct from `trace_missing`, which says nothing was compared. `licence_mismatch` is a finding kind and has its place in the closed set below.

`verify --all [--floor N]` checks every installed title with the checks above, then the console-wide checks. Each finding of a title is `finding <kind> <title> <detail>`, naming its title after its kind; `licence_missing` keeps the title as its detail. The console-wide findings are `finding <kind> <detail>`. `--floor N` names a free-space floor in bytes, and a floor is compared with the bytes available to an unprivileged process on the volume of `user/`; without `--floor` no space check runs. `--all` takes no title, no `--size` and no `--sha256`, and `--floor` is valid only with `--all`; any other option, a repeated option or a non-decimal floor answers `bad_option` (exit 1), and an extra operand answers `bad_argument` (exit 1), both before any check. A clean console answers the word `whole console` with exit 0; a console with any finding answers `not_whole console` with exit 1, after its findings. The sweep needs no approval and changes nothing on disk. An installed title is a directory under `user/app/`; a staging directory is a directory under `user/staging/`, and it is an orphan when no installed title has its name. A licence is an orphan when its name matches no installed title, the name containing `-<TITLE>_` for one of them. A store that cannot be listed for a reason other than its absence answers `unsupported` and is not a pass.

`trace NAME [--replace]` records the console's state under NAME, in `data/ariel/traces/records` under the state root, before it answers. The answer is the record in full, then `recorded NAME` and exit 0, and the kept file holds the same lines. The record has one line per field, in this order: `clock` (epoch seconds), `uptime` (seconds since boot), `free` (bytes available on the volume of the root), `mounts` with `mount <target> <source>` lines, `titles` with `title <name> <bytes>` lines (the bytes of the title's files), `metadata` with `metadata <name>` lines, `licences` with `licence <name>` lines, `running` with `running <name>` lines for each background payload, and `boot` (the epoch second the current boot began). Each count line gives the total, and each list shows at most 16 entries, so a console with many titles still answers under the output cap. Names and paths are escaped: a byte outside `0x21` to `0x7E`, and `%`, is written as `%XX`, and an escaped value is cut at 128 bytes. The verb needs no approval and changes nothing the owner owns. `NAME` is 1 to 32 printable ASCII bytes with no `/`, `\`, space, `.` or `..`; any other name answers `bad_path` (exit 1), and a name that is kept answers `trace_exists` (exit 96) unless `--replace` is given. The record carries no token, key material or approval state. The store keeps the 8 newest records; the oldest is dropped first, and records survive a restart. A bad option, a repeated option or an extra operand answers `bad_option` or `bad_argument` (exit 1), and no operand answers `missing_operand` (exit 1), all before anything is written.

`trace --list` answers one line `record <NAME>` for each record kept, in name order, then `exit 0`; with no record kept it answers nothing but `exit 0`. `trace --diff <NAME>` reads the console again and compares it with the record kept under NAME. It answers one line per changed field, `<field> <before> <after>`, with `absent` on the side where the field is missing, and then the count line `changed <n>` and `exit 0`. An entry is named by its field and its name: `licence fakeUP2611-CUSA00000_00.rif present absent` is a licence that was removed. The count of its list changes with it, and that changed count is a line of its own, `licences 1 0`. A diff with no change answers `trace_unchanged` and `exit 0`, never an empty answer. `clock` and `uptime` are not compared, because they move on every read. `free` is compared only when it moves by more than 16 MiB (16777216 bytes), because a record writes its own bytes to the volume, and `boot` only when it moves by more than one second, because it is derived from two whole-second readings. A `NAME` that is not kept answers `trace_missing` (exit 95). A bad name answers `bad_path` (exit 1). A missing operand, a repeated or unknown option and an extra operand answer the words above (exit 1), all before anything is read. Neither `--list` nor `--diff` writes anything.

Free from 97. The `status <n>` line is outside this registry.

## Finding kinds

A verification reports a problem as `finding <kind> <detail>`, and it reports only the kinds in this list. A kind outside it is not printed and is not a word a caller may branch on. `verify TITLE` emits `missing`, `empty`, `licence_missing`, `licence_mismatch`, `size_mismatch` and `hash_mismatch`; `verify --all` emits the same kinds for each title, and adds `licence_orphan`, `staging_orphan`, `space_below` and `unsupported`.

- `missing`: a required entry is absent. The detail names it, for example `missing app.xml`, or `missing content_id` when the title's `PARAM.SFO` has no `CONTENT_ID` entry.
- `empty`: a required entry is present and zero bytes.
- `licence_missing`: a title has no license under `/user/license`. The detail is the title.
- `licence_mismatch`: the content ID in the title's license file, `/user/license/fake<CONTENTID>.rif`, does not equal the `CONTENT_ID` entry of the title's `PARAM.SFO`. The detail is the license's file name.
- `size_mismatch`: the size of `app.pkg` is not the size the caller named with `--size`. The detail is `app.pkg` and its actual size.
- `hash_mismatch`: the SHA-256 of `app.pkg` is not the hash the caller named with `--sha256`. The detail is `app.pkg`. A hash is computed only when one is named.
- `licence_orphan`: a license names no installed title. The detail is the licence's file name.
- `staging_orphan`: a staging directory under `user/staging/` has no installed title of its name. The detail is the staging title.
- `space_below`: free space is below the floor the caller named with `--floor`. The detail is the bytes available.
- `unsupported`: a fact this firmware does not expose: a store (`licences`, `titles`, `staging`) that cannot be listed for a reason other than its absence, or `space` when the volume cannot be probed. The detail names the fact. It is never a pass.
